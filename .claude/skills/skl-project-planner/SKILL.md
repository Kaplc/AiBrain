# 项目计划文档生成器

## 工作流程

### 第一步：收集信息

用户给出一个项目或功能描述后，**先不要急着写文档**。分析描述中缺少的关键信息，提出 3-5 个针对性问题。问题要聚焦，不要问用户已经回答过的内容。

典型需要确认的维度：

- **目标用户**：谁在用？解决谁的什么问题？
- **核心场景**：最主要的 2-3 个使用场景是什么？
- **技术偏好**：有没有指定的技术栈、框架、数据库？
- **约束条件**：时间、预算、性能、兼容性等硬性限制？
- **边界**：什么明确不做？

用户回答后如果仍有模糊之处，可以追问一轮。最多两轮，然后进入生成阶段。

### 第二步：生成文档

在 `.claude/plan/` 目录下生成**一个 Markdown 文件**，文件名根据项目内容取一个简短的英文名（如 `.claude/plan/user-auth-system.md`）。

文件内部按以下 10 个章节组织，顺序固定，用 `# 一、项目目标` 这样的二级标题分隔：

```
# 一、项目目标
# 二、业务背景
# 三、功能需求
# 四、非功能需求
# 五、系统架构
# 六、数据结构
# 七、流程设计
# 八、API设计
# 九、验收标准
# 十、开发任务拆分
```

如果同名文件已存在，告知用户并确认是否覆盖。

### 第三步：自检

文档写完后，通读全文做一轮自检，重点检查：

1. **一致性**：第五章提到的技术栈、目录结构是否和第六章数据结构、第八章 API 对得上？有没有多出或遗漏的实体/接口？
2. **完整性**：第三章每个功能需求是否都有对应的 API（第八章）和验收标准（第九章）？是否有功能被遗漏？
3. **依赖合理性**：第十章任务拆分的依赖关系是否合理？有没有循环依赖或漏标依赖？
4. **数据流闭环**：第七章流程设计中的每个步骤，数据从哪来、到哪去，是否和第六章数据结构吻合？

发现问题直接修正，不用再问用户。如果发现用户描述中有逻辑矛盾或遗漏，在文档中标注"待确认"并告知用户。

### 第四步：各章节内容规范

根据用户描述和追问结果填充具体内容。内容要具体、可执行，不要写空洞的模板套话。

#### 一、项目目标
- 项目名称
- 一句话描述（做什么）
- 核心目标（3-5 条，每条可量化或可验证）
- 不做的事（明确边界）

#### 二、业务背景
- 问题现状：当前痛点是什么
- 目标用户画像
- 预期价值：解决后带来什么改善
- 可选：竞品或参考方案

#### 三、功能需求
按模块分组，每个功能用表格或列表描述：
- 功能名称
- 用户故事（作为XX，我想XX，以便XX）
- 优先级（P0 必须 / P1 重要 / P2 可选）
- 备注（特殊约束或依赖）

#### 四、非功能需求
- 性能要求（响应时间、并发量、数据量级）
- 安全要求（认证、授权、数据保护）
- 可用性要求（浏览器兼容、移动端适配、无障碍）
- 可维护性要求（日志、监控、部署方式）
- 如某项无特殊要求，写"无特殊要求"即可，不要编造

#### 五、系统架构
- 架构图（用 ASCII 或 Mermaid 画一个清晰的图）
- 技术栈选型及理由（表格形式）
- 目录结构（实际的文件/目录树）
- 关键设计决策及原因

#### 六、数据结构
- 核心数据实体（表格：字段名、类型、说明、约束）
- 实体关系（ER 图用 ASCII 或 Mermaid）
- 索引策略（哪些字段需要索引，为什么）
- 数据量预估

#### 七、流程设计
- 核心业务流程（每个流程用 Mermaid 流程图或步骤列表）
- 异常流程处理（失败场景和恢复策略）
- 状态流转（如有状态机，画出来）

#### 八、API设计
按模块分组，每个接口：
- 方法 + 路径（如 `POST /api/users`）
- 请求参数（表格：字段、类型、必填、说明）
- 响应结构（JSON 示例）
- 错误码

#### 九、验收标准
按功能模块列出验收条件，每条可测试：
- 功能验收（具体操作 + 预期结果）
- 性能验收（可量化的指标）
- 安全验收（需要验证的安全项）
- 交付物清单

#### 十、开发任务拆分
将开发工作拆成可独立执行的任务：
- 任务 ID（T001、T002...）
- 任务名称
- 依赖（依赖哪个前置任务）
- 预估复杂度（S/M/L）
- 所属模块
- 对应需求编号

按依赖顺序排列，能并行的任务分组标注。

## 写作原则

1. **具体胜过抽象**。写"用户点击按钮后 200ms 内显示结果"，不写"响应迅速"
2. **基于事实**。只写从用户描述和追问中确认的内容，不确定的地方标注"待确认"
3. **不要凑字数**。某个方面确实没有特殊要求就简短说明，不要为了篇幅编造需求
4. **章节之间保持一致**。架构要和数据结构、API 设计对得上，不能自相矛盾
5. **用中文写**。技术术语保留英文原文
