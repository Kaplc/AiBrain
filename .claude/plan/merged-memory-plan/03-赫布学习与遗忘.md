# Phase 2: 共现统计 — 联想触发器的数据源

## 精简说明

原始设计做了大量"模拟赫布学习"的机制：边权重动态调整、自动建边、遗忘曲线、记忆融合。

**实际改法**：只保留**共现计数**这个核心数据。不做边权重动态调整，不做自动建边，不做遗忘曲线。

## 只做一件事：统计哪些东西经常一起出现

在 `entity_relations` 表中增加计数：

```sql
ALTER TABLE typed_entity_relations ADD COLUMN co_activation_count INTEGER DEFAULT 1;
ALTER TABLE typed_entity_relations ADD COLUMN last_co_activated TEXT;
```

每次搜索时，如果多条结果共享同一实体，对应实体对的 `co_activation_count` +1。

## 共现数据怎么用——联想触发器的数据源

共现统计本身只是"原材料"。真正的应用是**联想触发器**（在 Phase 3 中实现）：

```
对话开始 → 提取话题实体 → 查共现统计 → 找到高频关联实体 → 召回关联记忆 → 注入 prompt
```

Phase 2 只负责：
1. ✅ 在 `typed_entity_relations` 中维护 `co_activation_count`
2. ✅ 提供查询接口：`get_related_entities(entity, top_k=5)`
3. ✅ 提供查询接口：`get_related_memories(entity, count_threshold=3)`

查询和召回的逻辑在 Phase 3 中实现。这里只把数据存好、可以查。

## 不做的事

| 原设计 | 不做原因 |
|--------|---------|
| 边权重动态调整 (`weight += 0.05`) | 权重的意义在于被"使用"，不是被计算 |
| 自动建 `entity_relations` 新边 | 概率性自动操作容易产生噪音 |
| 遗忘曲线衰减 | mem0 自身有降采样 |
| 记忆融合 | 已有 `dedup` 和 `organize` 功能 |

## 验证标准

- [ ] 多次搜索后，`co_activation_count` 正确增加
- [ ] `get_related_entities()` 返回正确的关联实体和计数
- [ ] `get_related_memories()` 返回高于阈值的关联记忆
- [ ] 不影响现有搜索和召回结果
