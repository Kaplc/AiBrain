# Phase 3: 联想触发器 — 对话开始时主动召回关联记忆

## 精简说明

原始设计用了一套复杂的"激活阈值检测"机制：每个节点有阈值 → 后台 tick 监控 → 突破时产生事件 → 注入对话。

**实际改法**：直接用 LLM 的自然联想能力。"涌现"不需要阈值检测——LLM 本身就会关联。

## 实现方案：联想触发器

不做阈值检测和 `emergence_events` 表。改用一个**对话开始时的主动召回**机制——在 LLM 开口之前，先把关联记忆喂给它。

### 3.1 触发时机

在每次对话开始时，PromptPipeline 的 `memory` section 之后，增加一个**关联召回**步骤：

```
PromptPipeline 执行顺序：

subconscious → self_narrative → [联想触发器] → memory → user message
                                        │
                                  在这里注入关联记忆
```

### 3.2 触发流程

```
用户消息 → 提取核心实体（extract_entities_llm）
               │
               ↓
   对每个实体调用 get_related_entities(top_k=5)
     → 得到 {关联实体: 共现计数} 列表
               │
               ↓
   用关联实体搜索记忆（search_memory）
     → 得到一批"历史关联记忆"
               │
               ↓
   去重 + 按共现计数排序 → 取 top 5
               │
               ↓
   注入 system prompt 的【背景关联】段落
               │
               ↓
   LLM 回复时自然带出："说起 X，我记得之前 Y……"
```

### 3.3 注入格式

```
【背景关联】
当前话题相关的历史关联：
- 「entity_relations」和「spreading_activation」经常一起出现
- 最近关于「link_entities」的记忆：

  2026年5月xxx: 那天下午你实现了 entity_relations 的边激活……

你可以自然地联想到这些方向，不要生硬。
```

### 3.4 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 触发时机 | 对话开始时 | 不是后台 tick，不是每句话都查，零持续开销 |
| 数据源 | `co_activation_count` | 已经持久化的历史共现，不需要实时计算 |
| 召回方式 | `search_memory` | 已有的向量搜索，不需要新检索方案 |
| 注入方式 | PromptPipeline section | 已有框架，不需要新中间件 |

**这个机制的本质是：用之前对话的共现数据，在当前对话开头主动召回关联记忆。** 它不需要后台线程、不需要阈值检测、不需要实时计算——但能让 LLM 在回复时看到具体的历史关联。

### 3.5 与 Phase 2 的关系

Phase 2 负责存数据（`co_activation_count` 维护 + 查询接口）。
Phase 3 负责用数据（触发召回 + 注入 prompt）。
两部分独立可测，但一起工作时才产生"联想"效果。

## 不做的事

| 原设计 | 不做原因 |
|--------|---------|
| 节点唤醒阈值 | 不需要——关联由共现统计决定，不是由激活值高低决定 |
| 后台 tick 检测突破 | 不需要——触发时机是对话开始时，不是随机时间 |
| `emergence_events` 优先级队列 | 不需要——关联记忆直接注入 prompt，不排队 |
| 涌现注入强度控制 | LLM 自己能判断该不该说 |

## 验证标准

- [ ] 对话开始时，topic 实体被正确提取
- [ ] `get_related_entities()` 返回的关联在 prompt 中出现
- [ ] LLM 回复时能自然引用关联记忆（"说到 X 让我想起 Y"）
- [ ] 关联记忆确实有历史共现依据，不是随机联想
